# バージョン管理ルールとビルドハッシュ表示機能 仕様書

対象: フロントエンド（FE）とバックエンド（BE）で構成されるクラブ用Webアプリ

## 1. 目的と前提

**目的**

- FEとBEの互換性を、バージョン番号で判断できるようにする
- 画面上でバージョンとビルドハッシュを確認でき、本番の改変・更新漏れに気づけるようにする
- 作者の離脱後も、次のメンバーがこのドキュメントだけで運用できるようにする

**前提（本書はこの前提で書いている）**

- FEとBEは別々にバージョンを持つ
- デプロイはFTPで行い、FEとBEの更新タイミングがずれる可能性がある
- BEはPHP、FEはHTML/JS。FEのファイルはBEと同じサーバーに置かれ、PHPから読める（要確認: 別ドメインに置く場合は10章の未決事項を参照）
- 正式版の置き場はGitHubリポジトリ。本番はそのデプロイ結果である

## 2. バージョン番号の基本ルール

形式は `MAJOR.MINOR.PATCH`（セマンティックバージョニング）。FEとBEは**独立して**番号を持つ。上の桁を上げたら、下の桁は0に戻す（例: 1.2.1 → 1.3.0 / 2.0.0）。

| 桁 | 上げる条件 | BEでの例 | FEでの例 |
| --- | --- | --- | --- |
| MAJOR | 互換性を壊す変更 | APIの入力受付を止める、同名APIの中身を非互換に変える、旧APIを削除する、APIの呼び方を変える | BEのMAJORに追従して必要になる大改修 |
| MINOR | 後方互換のある機能追加 | 新APIの追加、既存APIへの任意項目の追加 | 新しいBE機能を使い始めた、または画面の機能追加 |
| PATCH | その版の内側でしか意味を持たない修正 | 内部のバグ修正、性能改善（API仕様は不変） | 表示崩れ、文言、内部のバグ修正 |

**注意**: 「バグ修正」でも、同名APIの外から見た挙動が変わるなら、PATCHではなくMAJORまたは新API追加（4章）として扱う。迷ったら、CHANGELOGに理由を書いて判断を残す。

## 3. FEとBEの互換性ルール

**互換性の大原則**

- FE x.y.z は、BE の **x.y.0 以上、同じMAJORの範囲**で動く（「BE x.y.xまで」ではない。BEが新しくなっても旧FEは動く）
- 互換判定にPATCHは使わない

**判定表**

| 状況 | 扱い | 画面の挙動 |
| --- | --- | --- |
| BEのMAJORとFEのMAJORが一致、かつ使うAPIがすべてBEにある | 互換 | 何も表示しない |
| MAJORが一致、かつ使うAPIの一部がBEにない | 部分互換 | 警告を表示し、該当機能だけ無効化 |
| MAJORが不一致 | 非互換 | エラーを表示（全体を停止してよい） |

**「APIが存在するか」で判定する（機能一覧方式）**

バージョン番号の比較は推測にすぎないため、実際の判定にはBEが返す**機能一覧**を使う。バージョン番号は人間向けの目安、機能一覧はプログラム向けの判定材料と役割を分ける。BEは起動確認用に `GET /api/version` を提供する（7章）。

**導入バージョンの記録**

APIごとに「導入されたBEのバージョン」を記録する。記録先はCHANGELOGとする。

| API | 導入 | 状態 |
| --- | --- | --- |
| config | 1.0 | 現行 |
| new | 1.1 | 非推奨（2.0で削除予定） |
| new2 | 1.2 | 現行（newの新仕様） |

## 4. API変更のルール（新APIを並走させる方針）

MAJORの上昇を、「削除をまとめて行うタイミング」に集約する。

1. **追加は自由、削除と変更は慎重に。** 新機能は新しいAPI、または既存APIへの任意項目の追加で行う（MINOR）
2. **非互換な変更は、同名APIを書き換えず、新しい名前のAPIとして追加する**（MINOR）。旧APIはそのまま残す
3. **旧APIは非推奨（deprecated）にする。** CHANGELOGと機能一覧に印を付け、「削除予定のMAJOR」を明記する
4. **旧APIの削除は、次のMAJORでまとめて行う。** 同時に、APIの呼び方の変更など他の破壊的変更も同じMAJORに入れる
5. **FEは知らない項目を無視し、足りない項目には既定値を使う。** これでBEが項目を足してもFEは壊れない
6. **新機能の引数は任意にする。** 省略時は従来の動作とする
7. **新機能のデプロイ順は「BE → FE」。** 途中の状態でも壊れない

**履歴の例**

| 版 | 変更 | 区分 |
| --- | --- | --- |
| 1.0 | config を追加 | 初版 |
| 1.1 | new を追加 | MINOR |
| 1.2 | new の非互換な新仕様を new2 として追加（new は残す） | MINOR |
| 1.3 | config に項目を追加（非破壊） | MINOR |
| 2.0 | APIの呼び方を変更、非推奨の new を削除 | MAJOR |

**非推奨APIを残す期間**: 次のMAJORまで。MAJORを上げるまで削除しない。

## 5. バージョン表示の仕様

**表記**

```
Frontend | ver 1.0.0 (build 3b8a892)
Backend  | ver 1.2.1 (build 3a8b123)
```

- 表示場所: フッター、または設定画面の「バージョン情報」（要検討）
- buildは**7桁の16進数**（ハッシュの先頭7文字）
- FEとBEでbuildが異なるのは正常。それぞれ自分のファイルから計算する

**バージョン番号の置き場所**

- FE・BEそれぞれのルートに `VERSION` ファイルを1つ置く（内容は `1.2.1` の1行のみ）
- 画面表示・`/api/version`・CHANGELOGへの転記は、すべてこのファイルを正とする。複数箇所に手書きしない

## 6. ビルドハッシュの仕様（改変検出）

**目的**: ファイルが1バイトでも変わると値が変わるようにし、「本番が標準版と違う」「verの更新漏れ」に気づけるようにする。コミットIDではなく**ファイル内容から計算する**ため、FTPアップロードや本番の直接編集でも検出できる。

**計算方法**

1. 対象ディレクトリ配下のファイルを列挙し、除外対象（下記）を外す
2. 相対パス（区切りは `/`、UTF-8）の**昇順にソート**する
3. 各ファイルについて「パス + NULL文字 + 内容 + NULL文字」を順にSHA-256へ入力する
4. 結果の16進文字列の**先頭7文字**をbuildとして表示する（比較・記録には完全な64文字を使う）

**内容の正規化**

- テキストファイル（`.php` `.js` `.css` `.html` `.json` `.md` `.txt` など）は、改行の `CRLF` を `LF` に変換してから計算する。Windowsで編集しても値がぶれない
- 画像・フォントなどのバイナリは、そのままのバイト列で計算する
- リポジトリに `.gitattributes` を置き、テキストの改行をLFに統一する

**除外対象（初期案。実際のファイル構成に合わせて確定する）**

- `.git/` と、Git関連ファイル
- 設定ファイル（`.env`、認証情報、サーバー固有の設定）
- ログ、キャッシュ、一時ファイル
- ユーザーがアップロードしたデータ、データベースファイル
- ビルドハッシュの基準値を記録するファイル（`BUILD_REFERENCE`、6章後半）

`VERSION` は**対象に含める**（ver変更でもbuildが変わるようにするため）。

**キャッシュ**

毎回全ファイルを読むと遅いため、結果をキャッシュファイルに保存する。再計算のきっかけは、「対象ファイルの数・合計サイズ・最終更新時刻の最大値」のいずれかが変わったときとする。更新時刻を保ったままの書き換えは検出できないため、`tools/calc-build-hash.php`（下記）を手動実行すれば強制再計算できるようにする。

**共通の計算コード**

計算処理は1つのPHP関数にまとめ、次の2か所で同じものを使う。

- 本番での動的計算（`/api/version` から呼ぶ）
- リリース時の基準値作成（`tools/calc-build-hash.php` をコマンドラインで実行）

計算コードが2系統あると値が一致しなくなるため、必ず共通化する。

## 7. `/api/version` の仕様

`GET /api/version` はBEが返す。認証は不要とするが、返す内容は次の範囲に限る（内部パスや設定値は返さない）。

```json
{
  "backend": {
    "version": "1.2.1",
    "build": "3a8b123",
    "build_full": "3a8b123...（64文字）",
    "apis": {
      "config": { "since": "1.0" },
      "new": { "since": "1.1", "deprecated": true, "remove_in": "2.0" },
      "new2": { "since": "1.2" }
    }
  },
  "frontend": {
    "version": "1.0.0",
    "build": "3b8a892"
  }
}
```

- `frontend` はBEが同じサーバー上のFEファイルを読んで計算した値（前提どおり読める場合）
- `apis` は、ルーティング定義から生成するか、手書きする。手書きの場合は、API追加時に更新する（リリースチェックリストに入れる）

**FE起動時の処理**

1. `/api/version` を取得する
2. MAJORが一致するか確認する。不一致なら非互換エラーを表示する
3. FEが使うAPI名の一覧が、`apis` に含まれるか確認する。ないものは警告を表示し、該当機能を無効化する
4. `deprecated` のAPIを使っている場合は、開発者向けにコンソールへ警告を出す
5. 取得に失敗した場合は、バージョン表示を「取得できません」とし、アプリ本体は動作を続ける

## 8. 改変検出の運用

**基準値の記録（リリース時）**

リリースのたびに `tools/calc-build-hash.php` を実行し、FE・BEそれぞれの完全なハッシュを `BUILD_REFERENCE`（またはCHANGELOGのリリース欄）に記録する。

| 比較 | 意味 |
| --- | --- |
| 本番のbuild と、その版の基準値が一致 | 標準版そのまま |
| verは同じだがbuildが違う | 本番が直接改変されている、または一部のファイルの上げ忘れ |
| verもbuildも違う | 別の版が上がっている。標準版より古い、または新しい |

**表示での目印（任意）**: 本番が基準値と不一致のとき、`(build 3a8b123 *)` のように印を付ける。基準値は `BUILD_REFERENCE` から読む。

**限界（誤解しないこと）**

- これは**事故・更新漏れの検出**が目的であり、悪意ある改ざんの防止ではない。`BUILD_REFERENCE` ごと書き換えれば、一致して見える
- 除外対象のファイルの変更は検出されない

**改変が見つかったときの対応**

- 意図した改変なら、GitHubのクラブ用ブランチに反映して、正式な版として記録する
- 意図しないなら、GitHubの該当版でファイルを上書きして戻す

## 9. リリース手順チェックリスト

1. 変更内容に応じて、FE・BEそれぞれの `VERSION` を更新する（2章）
2. API追加なら、機能一覧（7章）とCHANGELOGの導入バージョン表を更新する
3. 非互換な変更は、新APIとして追加し、旧APIに非推奨の印を付ける（4章）
4. `tools/calc-build-hash.php` を実行し、基準値を `BUILD_REFERENCE` に記録する
5. CHANGELOGにその版の変更内容を書く
6. GitHubにコミットし、版のタグ（例: `be-v1.2.1`、`fe-v1.0.0`）を付ける
7. 本番にデプロイする。新機能なら**BE → FE**の順
8. 画面のバージョン表示で、バージョンとbuildが基準値と一致するか確認する

**CHANGELOGの書式**

```
## BE 1.2.0 (2026-11-06)
- 追加: new2 API（newの新仕様）
- 非推奨: new API（2.0で削除予定）
```

FEとBEで別ファイル（`CHANGELOG.md`）に分けるか、1つにまとめて見出しで区別するかは、リポジトリ構成に合わせて決める。

## 10. 未決事項

- **FEをBEと別ドメインに置く場合**: BEがFEのファイルを読めないため、FE側のbuild計算方法を別途決める（FEが自分のファイル一覧をJSで取得して計算する、リリース時に作ったマニフェストで代用する、など）
- **除外対象の確定**: 実際のファイル構成を確認して、6章の除外リストを確定する
- **機能一覧を手書きにするか自動生成にするか**: APIの数が多い場合は、自動生成を推奨する
- **バージョン表示の位置**: フッターか設定画面か
- **ハッシュ入力に使うバイト列の細部**: 文字コード（UTF-8のBOM有無）の扱いを実装時に決める
