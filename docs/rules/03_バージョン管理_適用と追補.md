規則 ID: `V1`〜。正は `vwc-rules`。

## 1. 位置づけ

- **`02_バージョン管理ルール_原文.md` を正とする。** 原文は一字も変えていない。
- 本書は、原文に対して次の3つだけを定める。
  1. FE・BE の2つで書かれた原文を、IdP を加えた**3つの配備単位**へ広げること

## 3. 互換性（3つの関係）

| 関係 | 判定 | 画面の挙動 | 根拠 |
|---|---|---|---|
| FE ↔ BE | 原文 §3 のとおり（FE x.y.z は、BE の x.y.0 以上・同じ MAJOR で動く。使う API が BE にあるかで判定） | 原文 §3 の判定表 | 原文 §3、`04` |
| BE ↔ IdP | `vwc_contract`（ID トークンの claim）が、BE の対応する契約番号に含まれるか。**契約番号 = IdP の MAJOR** | 合わなければログインを止め、画面に `E-A20` を出す（`04` §11、IdP 契約） | IdP 契約 |
| FE ↔ IdP | 直接の契約はない（B15）。BE の入口への遷移と `?auth=` への反応だけ | — | B15 |

- IdP が claim を**足す**のは、互換のある変更（MINOR）。BE は知らない claim を無視する。
- IdP が claim を**消す・意味を変える**のは、互換を壊す変更。IdP の MAJOR を上げ、契約番号を新しくする。移行の間、IdP は旧契約のまま発行できるようにする（IdP 契約の `clients` ごとの `contract` 設定）。

## 6. MAJOR リリースの手順（V-R9）

1. 事前に、利用者へ「○日○時ごろ、数分間、エディターが使えなくなる」と、お知らせ（`announcements`）で伝える。
2. 配備の順は **BE → FE** を続けて行う（2つの間の時間を最小にする。作業は事前に手元で用意する）。
3. 合間に、画面は「サーバーとエディターの版が合いません」を出す（現行 FE の既存動作）。これを異常とみなさない。
4. 両方を置き終えたら、バージョン表示（FE・BE）と build が、基準値と一致することを確認する。
5. 戻すときは、2つを前の版へ、同じ順で戻す。

## 7. 検査対象と除外対象（原文 §6 の確定）

### 7.1 共通

- 全テキストファイルは、改行 `CRLF` → `LF` に変えてから計算する。ほかのバイト（BOM を含む）は**変えない**。孤立した `CR` は変えない。
- テキストの判定は、**拡張子（大文字小文字を区別しない）が次のいずれか**、または**ファイル名が次のいずれか**。
  - 拡張子: `.php .js .css .html .json .md .txt .svg .xml .yml .yaml .sh .py`
  - ファイル名: `VERSION` `.htaccess` `.gitattributes`
  - それ以外はバイナリ（そのままのバイト列）
- 各リポジトリに `.gitattributes` を置き、上のテキストの改行を LF に統一する（原文 §6）。
- 相対パスは配備単位のルートからの `/` 区切りの UTF-8。**UTF-8 のバイト列の昇順**で並べる（ロケールに依存させない）。
- `VERSION` は対象に含める（原文 §6）。`BUILD_REFERENCE`・`build-manifest.json` は含めない。
- **基準値の配備**（BE・IdP）: 配備のとき、`BUILD_REFERENCE` の `build_full` を、`system/config/build_reference.txt`（1行）に書く。画面や管理画面が、計算した build とこの値を比べて、一致・不一致の印を出す（原文 §8「表示での目印」）。`build_reference.txt` は、7.2・7.3 で**検査の対象から除外する**。除外しないと、基準値を書くたびに build が変わり、永久に一致しなくなる（循環）。`system/config/` の他のファイル（`config.sample.php` と `.htaccess`）は、配布物なので対象に含める。

### 7.2 BE（配備単位のルート = サーバーの `editor/`）

BE が所有するパス（`01` §3 の所有表）だけを対象にする。**FE のファイルは含めない**（B6）。

- 対象: `system/**`、`file/.htaccess`、`app/.htaccess`
- 除外: `system/config/config.php`、`system/config/build_reference.txt`、`system/data/**`（ただし `system/data/.htaccess` は対象）、`system/setup.php`（初期設定後に消える）、`file/` と `app/` の中の利用者のデータ（`.htaccess` 以外）、`*.log`
- 計算は `meta/version` が行う（キャッシュあり。原文 §6）。基準値は `tools/calc-build-hash.php` で作る。

### 7.3 IdP（配備単位のルート = サーバーの `auth/`）

- 対象: `auth/**`
- 除外: `system/config/config.php`、`system/config/clients.php`（秘密を含む）、`system/config/build_reference.txt`、`system/data/**`（ただし `system/data/.htaccess` は対象）、`setup.php`、`*.log`
- 計算は `version.php` が行う（キャッシュあり）。

### 7.4 FE（配備単位のルート = `public/`）

FE は PHP を持たず、ブラウザーから読めるファイルだけが検査できる。

- 対象: `public/**` のうち、ブラウザーから取得できる**中核のファイル**
- 除外: `config.js`（環境ごとの設定）、`.htaccess`（ブラウザーから取れない）、`vendor/**`・`fonts/**`・`help/media/**`（第三者の資材や大きなファイル。固定した SHA-256 を `tools/complete.py --verify` が検証する）、`build-manifest.json`
- `.htaccess` を検査できないことは、原文 §8 の限界として受け入れる（CSP などの設定の改ざんは、この仕組みでは見つからない）。
- **作り方:** リリース時に `tools/calc-build-hash.py` が、`build-manifest.json`（`version`・`build`・`build_full`・`files{パス: SHA-256}`）を作り、`public/` に置く。`complete.py` の実行後に作る。
- **表示:** 設定画面は `VERSION` と `build-manifest.json` を読んで、`ver` と `build` を出す。
- **検査:** 設定画面の「整合性を確認」ボタンで、対象の各ファイルを取得して SHA-256 を計算し（テキストは 7.1 の正規化）、`build-manifest.json` と比べる。**不一致・欠落があれば `(build 3b8a892 *)` と、差のあるファイル名を出す。** 実行できなかった場合は「確認できません」と出し、アプリの動作は続ける（原文 §7-5）。
- 限界: `build-manifest.json` ごと書き換えられると一致して見える（原文 §8）。FTP で**追加**されたファイルは、一覧が取れないため見つからない。

## 8. 適合テストベクタ（3つの実装が同じ値を出すことの確認）

BE・IdP（PHP）と FE（Python・JS）は、別々に実装する（V-R4）。次の6つのファイルから計算した結果が、下の値と**完全一致**することを、各リポジトリの自動テストで確認する。

| 相対パス | 内容（バイト列） |
|---|---|
| `.htaccess` | `Require all denied` + `CR LF` |
| `VERSION` | `1.2.1` + `CR LF` |
| `img/dot.bin` | 6バイト: `00 01 02 0D 0A FF`（バイナリなのでそのまま） |
| `index.php` | `<?php` `CR LF` `echo "ok";` `CR LF` |
| `lib/a.js` | `var a=1;` + `LF` |
| `日本語/と.txt` | `テスト` + `CR LF`（UTF-8） |

- 並び順（UTF-8 のバイト昇順）: `.htaccess`、`VERSION`、`img/dot.bin`、`index.php`、`lib/a.js`、`日本語/と.txt`
- **完全なハッシュ（64文字）**: `c6e66df436462b6024f6e0c40d6a36b5e1b035db5acef5b14b4d12991275af37`
- **build（先頭7文字）**: `c6e66df`
- 追加の確認: ① テキストの `CR LF` を `LF` に替えても値が変わらない。 ② `img/dot.bin` を `00 01 02 0A FF` に替えると値が変わる（バイナリは正規化しない）。 ③（BE・IdP）`system/config/build_reference.txt` を置く・書き換えても、build が変わらない。 ④（BE・IdP）`system/config/config.php`・`system/data/` の中身を変えても、build が変わらない。

手順（言語によらない）:

```text
files = 検査対象のファイルを列挙し、除外を外す
sort files by UTF-8 bytes of 相対パス
h = SHA-256()
for f in files:
    h.update( UTF-8(相対パス) + 0x00 + 正規化(内容) + 0x00 )
build_full = h.hexdigest()   # 64文字
build      = build_full の先頭7文字
```

## 9. 公開する形（要約。正は `04` と IdP 契約）

- BE: `meta/version` の `backend` ブロック（`version`・`build`・`build_full`・`apis`）。`04` §9。
- IdP: `GET /auth/version.php` の `idp` ブロック（`version`・`build`・`build_full`・`contract`・`endpoints`）。IdP 契約。
- 返してよいのは、版・build・API 名・導入版・非推奨の印だけ。内部パスや設定値は返さない（原文 §7）。

## 10. 版を上げる判断（本システムでの例）

| 変更 | 区分 | 理由 |
|---|---|---|
| `meta/version` に `backend` を足す | BE MINOR | 追加で、旧 FE は無視する |
| 新しい API ルートを足す（例: `auth/…`） | BE MINOR | 追加 |
| 既存 API の任意の入力キーを足す | BE MINOR | 追加。`params_since` を記録 |
| レジストリの導入（API の外から見える挙動は変わらない）、文書の訂正 | BE PATCH | 内側の変更 |
| `microsoft.php`・`admin/device_revoke`・別名のキー（`mail`／`email` など）・`features[]` の削除 | BE MAJOR（2.0.0） | 外から見える削除（v2 現状: 実施済み） |
| 設定画面にバージョン情報を足す | FE MINOR | 画面の機能追加 |
| Microsoft の画面と `requiredApi` の廃止 | FE MAJOR（2.0.0） | BE 2.x を要求する（v2 現状: 実施済み） |
| IdP の claim を足す・画面の修正 | IdP MINOR／PATCH | — |
| IdP の claim を消す・意味を変える | IdP MAJOR | 契約番号が変わる |

## 11. `CHANGELOG.md` の書式

原文 §9 の書式のとおり。見出しに、対象（`FE` `BE` `IdP` `RULES`）・版・日付を書く。リポジトリごとに別ファイルにする。

```text
## IdP 1.0.0 (2026-12-01)
- 追加: 認可コード＋PKCE（authorize / token / jwks）
- 追加: TOTP（登録・検証）
```
